# Release

## Status

Accepted. The workflow has not run on GitHub yet: nothing is published, and the repositories, the GitHub App and the Packagist entries it needs do not exist yet ([RELEASING.md](../../RELEASING.md)).

## Context

A release publishes four Composer packages (`packages/*`) and the extension's PIE package (`extension/`). Packagist publishes a package from the root of a repository only, so each one needs a read-only repository of its own that the release fills from this one; PIE also looks for the extension's prebuilt archives on the GitHub release of the extension's repository ([Prebuilt Extension Binaries](0030-prebuilt-extension-binaries.md)).

A release should be one run, started by hand in CI, that does everything else, after the pattern of `sagikazarmark/atuin-worker`'s release workflow (a manual run on `main` that picks the version with `sagikazarmark/next-version`, runs the build and tests as a reusable workflow, attests the artifact and creates the GitHub release). Nothing is published from a developer's machine.

## Decision

1. **Lockstep: one version for every package and the extension.** Release `X.Y.Z` tags this repository `vX.Y.Z`, every package repository `vX.Y.Z` and the extension repository `X.Y.Z` (bare: PIE puts the tag in the asset names, [Prebuilt Extension Binaries](0030-prebuilt-extension-binaries.md) decision 11), and the extension reports `X.Y.Z`. Users install the same version of both, and there is one compatibility table ([Extension Versions](../EXTENSION_VERSIONS.md)). The cost: a release rebuilds and republishes the extension even when it did not change, and a new minor version of the SDK needs the new minor of the extension. The versions can be split again later (at 1.0, say).
2. **`restate/sdk` requires the extension of its own minor version: `~X.Y.0`** (`~0.1.0` now). Within a minor version, patch releases of either side work together; a contract version change ([Extension Versions](../EXTENSION_VERSIONS.md#how-to-bump)) therefore needs a new minor version, which the workflow checks. `~X.Y.0` reads the same before and after 1.0, where `^X.Y` would accept every later minor.
3. **The version is in the tree: the extension's crate version** (`extension/extension/Cargo.toml`). The module compiles it in (`ext-php-rs` registers `CARGO_PKG_VERSION`; `Restate\Extension\version()` returns it), so the release cannot pass it at build time without editing files, and the split extension repository's sources then say the version they were released as. A release starts with a commit that sets it (`extension/Cargo.lock` follows; the archives are built with `--locked`) and, for a new minor version, `restate/sdk`'s constraint; `composer check:packages` fails when the constraint is not `~X.Y.0` of the crate version. The workflow has no version input: [`sagikazarmark/next-version`](https://github.com/sagikazarmark/next-version) only checks the crate version (not a tag yet, newer than the latest `vX.Y.Z`) and gives the previous tag and whether it is the latest release.
4. **One workflow, `.github/workflows/release.yaml`, run by hand on `main`** (`workflow_dispatch`; one release at a time):
   1. **version** reads and checks the version, then the tree: `restate/sdk`'s constraint is `~X.Y.0`; the contract version (`CONTRACT_VERSION` in the extension crate) is the previous release's unless the minor version changed; every directory it publishes has a `README.md` and a `LICENSE`.
   2. **ci** and **upstream** run `.github/workflows/ci.yaml` and `upstream.yaml` on the release commit (they are reusable workflows, `workflow_call`). The `skip-tests` input skips them, as an escape hatch.
   3. **extension** runs `.github/workflows/extension.yaml`, the 24 archives with their checks (it only builds; it also runs on changes to `extension/` and by hand); **attest** checks that they are of the release version, writes `SHA256SUMS` and attests them (`actions/attest-build-provenance`; the provenance is recorded in this repository) and names the bundle `php_restate-X.Y.Z.sigstore.json`.
   4. **publish** (environment `release`, after every job above passed or was skipped) publishes in dependency order: the extension repository (split, tag `X.Y.Z`, a release with the archives, `SHA256SUMS` and the bundle, created as a draft and published once complete, since PIE sees published releases only and immutable releases accept no assets after publishing); then each package repository (split, tag `vX.Y.Z`); then this repository's release `vX.Y.Z` with generated notes, which creates its tag. The extension comes first so that the packages, which Packagist picks up within minutes, never require an extension that cannot be installed yet.
5. **Split with `git subtree split`**: the history of the directory, on the repository's `main`, fast-forward only.
   - **Why it:** it is built into git, needs no other tool, and keeps each file's history in the package repository. It gives the same commits every time, so a re-run pushes nothing new. git documents that guarantee, and its maintainers treat changing the split commits as breaking. All five directories together take about a minute.
   - **`bin/split.sh` does it** (`composer release:split`): `list` names the directories and their repositories, `split` prints the split commits of HEAD, and `publish --version X.Y.Z --remote <url>` pushes and tags (without `--version` it pushes `main` only, decision 9). The publish job runs it, and anyone can run it locally: `publish --dry-run` against the real repositories says what a release would push, and a rehearsal against local bare repositories (`file://`) does it.
     - It checks a repository's `main` and the release tag before pushing anything for that directory.
     - It never passes `--annotate`, `--rejoin` or a signing option, and refuses an `i18n.commitEncoding` other than UTF-8. Each of these would change the split commits.
   - **Rejected, with the details in [Subtree split tooling](../research/subtree-split-tooling.md):**
     - **`splitsh-lite`.** Faster. Laravel uses it; Symfony splits through a hosted service, split.sh, and does not document what that runs. Its commits differ from `git subtree split`'s on some merges, and in a measured history a split taken at an earlier commit was not an ancestor of the later one: a second release would have been refused. It has no release binaries and is not in nixpkgs.
     - **`danharrin/monorepo-split-github-action`.** It copies the directory as one new commit per run, so the package repositories have no file history. A re-run commits nothing when the files are unchanged, but would probably fail creating the tag that already exists (read from its source, not run).
     - **josh and Copybara.** They never reproduce `git subtree split`'s commits.
   - **If the split ever gets slow:** git-filter-repo (`--subdirectory-filter <dir> --preserve-commit-hashes --prune-empty always --prune-degenerate always`) produced exactly `git subtree split`'s commits on the measured histories, in about 3 s instead of about 106 s on 7,852 commits. Neither project guarantees that match, so verify it on this repository's history before switching.
6. **Re-runnable, never forced.** A repository's `main` only moves forward (a `main` that already contains the release's split, the split of a later commit, is left alone and the tag goes on the release's split); a tag that exists on the same commit is skipped and one on another commit stops the release; the extension release is uploaded to again while it is a draft and left alone once published; this repository's release is skipped when it exists. "Re-run failed jobs" finishes a release that stopped halfway. Nothing is force-pushed: a package repository that someone pushed to stops the release until it is repaired by hand.
7. **A GitHub App pushes.** `actions/create-github-app-token` mints a token for the job that can only write the contents of the five repositories (`permission-contents: write`, the repositories listed in the workflow); it is not tied to a person's account and does not expire like a personal token. This repository's release uses the workflow's own token. The repositories are listed once, by `bin/split.sh list` (directory and repository name), which the workflow reads, all owned by the `RELEASE_OWNER` variable, `restate-php`, which also owns this repository (`restate-php/restate`). Each is named like its package without the vendor (`restate/sdk` is `restate-php/sdk`): `ext-restate`, `common`, `ingress`, `sdk`, `testing`.
8. **Actions are pinned by commit** in the release workflow (it holds the App's key), with the version in a comment; the other workflows still pin by tag ([TESTING.md](../../TESTING.md#ci)).
9. **Every push to `main` updates the repositories' `main`** (added 2026-11-23): `.github/workflows/split.yaml` runs `bin/split.sh publish --remote <url>` without `--version`, on pushes to `main` that touch `extension/`, `packages/`, `bin/split.sh` or the workflow, hourly (a retry net for failed runs and for pushes the paths leave out), and by hand. It tags nothing.
   - **Why:** most PHP monorepos split on every push (Laravel, API Platform, OpenTelemetry PHP, Symfony through split.sh; Filament and Sylius split only when they release). Composer's `dev-main` of every package then follows this repository, so users can try an unreleased fix (`self.version` needs no branch alias, [Package Split](0029-package-split.md) decision 4), and a repository that someone pushed to stops a merge's run, not a release halfway.
   - **A release of a commit that later pushes passed.** A release takes as long as its slowest test job, and anything merged meanwhile gets split and pushed. `publish --version` therefore leaves a `main` that contains the release's split alone and tags the split. It cannot tell such a `main` from commits pushed by hand on top of the split; the push workflow can, since it splits the tip of `main`: without `--version`, a `main` that contains the split and more stops the run (and a `main` that does not contain it stops both). The hourly run catches such a commit even when the directory has not changed since.
   - **Races.** The workflow does not share `release.yaml`'s concurrency group, which would let a push cancel a pending release; its own runs go one at a time, a newer pending run replacing an older one. When a push of `main` fails, `bin/split.sh` fetches `main` again and goes on if it now contains the split (the other workflow pushed a later one); otherwise it stops.
   - **The App's key: the `release` environment, for now.** One environment holds the key and its variables. Required reviewers on it would hold every push run for approval too; a second environment (`split`, deployment branches limited to `main`, no reviewers) would let the push runs go unattended while releases keep their approval, at the cost of the key in two places. The job only checks out, lists the repositories and runs `bin/split.sh`, with actions pinned by commit.
   - **Off until the repository variable `SPLIT_ON_PUSH` is `true`**, set once the repositories and the App exist ([RELEASING.md](../../RELEASING.md)); a manual run works either way.
   - **Costs:** about a minute per run, growing with the history (decision 5's fallback applies). Between a new minor version's version commit and its release, `dev-main` of `restate/sdk` requires an extension (`~X.Y.0`) that has no release yet, so it installs only with the extension built from source.

## Verification

- `actionlint` (in `composer check:scripts`) passes on every workflow.
- `composer test:release` (part of `composer check`; `tests/Unit/Release/SplitScriptTest.php`) runs `bin/split.sh` on a throwaway monorepo, pushing to local bare repositories (`file://`) instead of GitHub:
  - A release pushes every directory's history and tag (the extension's bare) and a re-run pushes nothing.
  - The next release fast-forwards `main` and keeps the earlier tag.
  - A tag already on another commit, or a `main` changed by hand, stops the run before that directory is pushed.
  - A dry run reports every directory and pushes nothing.
  - The splits keep a merge that touched the directory and leave out commits that did not.
  - Without a version, a run pushes every `main` and no tag, and a re-run pushes nothing.
  - A release of an earlier commit, after a push from another checkout put a later split on `main`, leaves `main` alone and tags its own split; so does a release whose push loses a race with such a push (a `pre-push` hook pushes the later split between the check and the push).
  - A commit pushed by hand on top of a split stops a run without a version.
- `composer check:packages` fails with `restate/sdk must require ext-restate ~0.1.0, the minor version of the extension crate, not '^0.1'` when the constraint lags the crate version.
- The version job's tree checks, run locally: they report every published directory without a README or LICENSE; against a throwaway local tag `v0.1.0` whose `CONTRACT_VERSION` was 0, releasing `0.1.1` fails ("The contract version changed since v0.1.0 (0 -> 1): release a new minor version") and `0.2.0` fails until `restate/sdk` requires `~0.2.0`.
- Not verified: anything on GitHub (the App token, the reusable workflow calls, the attestation, the release creation and publication, Packagist picking up the tags), because no job has run there yet.

## Consequences

- Releasing is one manual run after a version commit; nothing is published from a developer's machine.
- With `SPLIT_ON_PUSH` on, the repositories' `main` follows this repository's `main`, and `dev-main` of every package is installable; a release then mostly tags.
- Every release publishes 24 extension archives, also when only PHP code changed, and every new minor version of `restate/sdk` needs the same new minor of the extension.
- The release takes as long as its slowest test job (the integration and FrankenPHP suites, the upstream suite) plus the arm64 and musl builds.
- Adding a package means a line in `SPLITS` in `bin/split.sh`, a repository, the App's installation on it and a Packagist entry.
