# Pause

## Status

Accepted. Builds on [Shared Core](0014-shared-core.md) (the run completion heuristic), [Exception Hierarchy](0015-exception-hierarchy.md) and [Runtime Execution Hooks](0017-runtime-execution-hooks.md).

## Context

Restate 1.8 (service protocol v7) can **pause** an invocation instead of retrying it: the attempt ends, the invocation sits in status `paused`, and nothing runs until someone resumes it (CLI, UI, or the admin API's `PATCH /invocations/{id}/resume`, which may also move it to a newer deployment). Restate pauses on its own when an invocation retry policy with `onMaxAttempts: PAUSE` gives up (`InvocationRetryPolicy::ON_MAX_ATTEMPTS_PAUSE`, discovery metadata). The question is how handler code asks for a pause.

What shared-core 8.x offers:

- `Error::with_should_pause(true)` sets `ErrorMessage.behavior = PAUSE`. `notify_error` refuses it below v7: it fails the attempt with 573 "Feature 'error behavior' is not supported by the negotiated protocol version …" (the caller's message is lost) and writes behaviour `RETRY`.
- `OnMaxAttempts::Pause` on a `FixedDelay` or `Exponential` run retry policy: once the policy is exhausted, `propose_run_completion` sets the behaviour to pause, relates the error to the run command, and returns the submitted error, exactly what it returns for a scheduled retry. Below v7 any proposal under such a policy (even a success) fails with 573 "Feature 'pause' is not supported …".
- No structured run-completion result, and the error's behaviour is crate-private ([Run completion heuristic](0014-shared-core.md#run-completion-heuristic)).

What the official SDKs expose (TypeScript `492920d`, Java `6b0a96c`, Python `377d634`):

- **TypeScript**: `class PauseError extends RestateError` (`message`, `{errorCode?, cause?}`, `PauseError.from(cause)`), documented as "MUST be used only within a `ctx.run` closure". In a run it proposes the failure with `with_should_pause(true)` under an infinite retry policy: shared-core's retry branch keeps the behaviour, so the attempt ends with a pause and no version check runs (on v6 Restate ignores the unknown field and retries). Thrown from the handler it is logged ("leads to pause loops") and reported as a plain retryable error. `asTerminalError` cannot return it. `onMaxAttempts: "pause" | "kill"` exists only on the invocation retry policy.
- **Java, Python**: no pause error; only the invocation retry policy's `onMaxAttempts`.
- **`restatedev/e2e` v2.3**: no SDK pause cases; its `PauseResume*` tests are server tests with Java services.

## Decision

1. **`Restate\PauseError`** (`extends \RuntimeException implements Restate\Exception`, not final, like `TerminalError` and `RetryableError`): `new PauseError(string $message, ?\Throwable $previous = null)`. TypeScript's name. No status code: the handler path reports 500 like any error, so a code would only work in runs.
2. **It pauses from a run and from a handler.**
   - In a `Context::run()` callback (core `Vm::propose_run_pause`): the failure is proposed under a policy that leaves shared-core no outcome but pause (`FixedDelay`, no attempts allowed, `OnMaxAttempts::Pause`), whatever the run's own policy. The error message carries `behavior = PAUSE` and the run as related command; the run records no result and executes again on resume. Going through the pausing policy instead of TypeScript's `with_should_pause` plus an infinite policy keeps shared-core's v7 check, so v6 fails clearly (see 4) rather than silently retrying.
   - From a handler (core `Vm::notify_pause`): `notify_error` with `with_should_pause(true)`.

   **This differs from TypeScript**, which ignores a handler-level `PauseError` because "it leads to pause loops": code outside `ctx.run` is deterministic, so resuming without a code change pauses again. That loop is what a pause is for, though: the invocation waits for a person, and resuming it on a new deployment (the admin API's `deployment` parameter) is Restate's own workflow for fixing a bug in a stuck invocation. Silently retrying instead would surprise the user who threw it and burn attempts. An error mapper returning `PauseError` for, say, `\LogicException` turns "retry a bug forever" into "pause until fixed", which is only possible at handler level.
3. **Run retry policies may pause once exhausted:** `RunRetryPolicy::fixedDelay(…, onMaxAttempts: OnMaxAttempts::Pause)` and `RunRetryPolicy::exponential(…, onMaxAttempts: …)`, with the enum `Restate\OnMaxAttempts { Fail, Pause }` (shared-core's names; `Fail` is the default). The Extension Surface's retry policy shape carries `on_max_attempts: 'fail'|'pause'`. No official SDK exposes this for runs; it is a shared-core feature, and it fits Restate's own `onMaxAttempts` on the invocation retry policy. `none()` and `infinite()` have no "exhausted" state and take no option. (The invocation retry policy keeps its manifest strings `PAUSE`/`KILL`.)
4. **Below protocol v7 (Restate 1.7) a pause fails the attempt with 573, and Restate retries it.** There is no way to express a pause, and degrading silently would be wrong both ways: failing terminally is destructive, retrying silently hides that the server is too old. For an explicit pause (`PauseError`) the core checks the negotiated version itself and fails with 573 and "Pausing the invocation needs service protocol v7 (Restate 1.8 or newer), but this invocation negotiated v6; failing the attempt instead: <the PauseError's message>", since shared-core's own refusal names its internal feature ("error behavior") and drops the message. In a run, `Context::run()` then throws the `BackendException` (protocol, 573). A pausing run policy is refused by shared-core itself ("Feature 'pause' is not supported …") at the first retryable failure, also while attempts are left; the core passes the policy without the pause for a success or terminal failure (which never use it), so a run that succeeds is unaffected on 1.7. Restate 1.7 shows the failure as `last_failure` "[573 Unsupported feature] …" with status `backing-off`.
5. **The run completion heuristic does not claim a retry.** Under a pausing policy, `propose_run_completion` returns the submitted error both for a scheduled retry and for the pause, and nothing public tells them apart. So the outcome is `RunRetryOutcome::AttemptEnded` (extension `'attempt_ended'`, PHP `RunCompletionStatus::AttemptEnded`): "the run did not complete and the attempt must stop". The PHP side does the same in both cases: it ends the attempt as after a suspension (`SuspensionGuard` marks it, `Context::run()` throws the internal `SuspensionException`, the endpoint writes nothing more), and the error message the VM wrote tells Restate which it is. Where reporting differs:
   - **Run result**: none in either case; the run executes again on the next attempt (after the retry delay, or after resume).
   - **Hooks**: run interceptors see the callback's exception (`RetryableError`, `PauseError`, or the raw exception); handler interceptors see a suspension (`Suspension::is()`), for a retry as for a pause.
   - **Messages**: the internal `SuspensionException` says "Run retry scheduled." under a policy that does not pause, "Run retry scheduled, or the invocation paused because the run retry policy is exhausted." under one that does, and "Run paused the invocation." for a `PauseError` (whose outcome the core knows: `run::pause_outcome`). The SDK's log does not claim one either ([SDK Logging](0027-sdk-logging.md)): under a pausing policy the run's warning says "Restate retries it, or pauses the invocation once the run retry policy is exhausted", and the endpoint logs the end of the attempt as a suspension. Restate logs the pause or the retry from the error message.

   The pinning test `a_policy_pauses_once_exhausted_only_when_asked` covers it. The heuristic goes away once shared-core reports the outcome (retry scheduled, paused, completed) itself.
6. **The error mapper may return a `PauseError`** (`ErrorMapper::map(): TerminalError|RetryableError|PauseError|null`), from handlers and runs, and never sees one.

The Extension Surface has `Vm::notifyPause(message, stacktrace)`, `Vm::proposeRunPause(handle, message, attempt_duration_millis)` and the retry policy's `on_max_attempts`, and `proposeRunRetryable` answers `attempt_ended`; the Backend Contract has `Invocation::notifyPause()` and `InvocationOperations::proposeRunCompletionPause()`.

## Consequences

- Public API: `PauseError`, `OnMaxAttempts`, the `onMaxAttempts` parameter of `RunRetryPolicy::fixedDelay()`/`exponential()`, and `PauseError` in `ErrorMapper::map()`'s return type. `RunRetryPolicy::toArray()` (internal) always carries `on_max_attempts` for bounded policies.
- Pause needs Restate 1.8; on 1.7 it fails every attempt that asks for it, visibly.
- Evidence: core VM tests `tests/vm/pause.rs` (v7 frames for a handler pause, a run pause, a pausing policy before and after exhaustion, exponential by duration, retry-after keeping the pause; v5/v6 refusals; success and terminal failure under a pausing policy on v6) and the `run.rs` unit tests; extension suite `ExtensionPauseTest` (frame bytes with `behavior = PAUSE`, 573 frames and exceptions); unit `PauseTest` (run and handler paths, error mapper, interceptors, the guard, the refused case, the message under a pausing policy); integration `PauseTest`: on Restate 1.8.1 a `PauseError` from a handler, from a run, from an error mapper, and a run policy exhausted after two attempts each leave the invocation `paused` after exactly the attempts that asked (none after), and `PATCH /invocations/{id}/resume` after fixing the condition completes it; on 1.7.14 each fails with "[573 Unsupported feature] …" and keeps `backing-off`.
