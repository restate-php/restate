# Scope and Limit Key

## Status

Accepted. Builds on [Shared Core](0014-shared-core.md) (protocol v7), [Pause](0021-pause.md) (the same kind of version refusal) and [Ingress Client](0022-ingress-client.md).

## Context

Restate 1.8 adds flow control. A **scope** groups invocations, virtual object instances and workflow runs (typically per tenant) and is part of the target's identity: the identity tuples become `scope, service, handler, idempotencyKey?`, `scope, object, key, handler, idempotencyKey?` and `scope, workflow, key, handler`. An object or workflow key, and an idempotency key, therefore name a different instance in each scope and outside any scope, and the scope contributes to the partition key, so everything in one scope is co-located. A **limit key** (one or two levels, `tenant1` or `tenant1/user42`) is not part of the identity; together with the scope it is what the cluster's **rule book** matches (`restate rules set "checkout/*" --concurrency 10`, patterns `scope/L1/L2` with `*`, the most specific rule wins, an invocation counts against every level it touches). Both values are `[a-zA-Z0-9_.-]`, 1 to 36 bytes per level, and a limit key needs a scope ([flow control](https://docs.restate.dev/services/flow-control); the 1.8.1 ingress answers "bad scope value: value contains characters outside the allowed set [a-zA-Z0-9_.-]" and "value too long: 37 bytes (max 36)").

Protocol (shared-core 8.x, `service-protocol/…/protocol.proto`): v7 adds `scope`/`limit_key` to `CallCommandMessage` (fields 7, 8) and `OneWayCallCommandMessage` (8, 9), `scope` to `WorkflowTarget` (3) and `IdempotentRequestTarget` (5), and the three values to `StartMessage`. shared-core's `Target` has `scope` and `limit_key`, `AttachInvocationTarget::WorkflowId`/`IdempotencyId` have `scope`; it rejects empty values (`HitError`, 500) and, below v7, fails the attempt with 573 "Feature 'scope' is not supported by the negotiated protocol version 'V6', the minimum required version is 'V7'". It does not check that a limit key has a scope.

What the official SDKs expose (TypeScript `492920d`, Java `6b0a96c`, Python `377d634`), all marked preview/experimental:

- **TypeScript**: `ctx.scope(key)` returns a `ScopedContext` (the service/object/workflow client factories, `client`/`sendClient`); `limitKey` is a call/send option (`rpc.opts({limitKey})`, `rpc.sendOpts`); `genericCall`/`genericSend` take `scope` and `limitKey`; the request exposes `scope` and `limitKey`. The ingress client has `connect(…).scope(key)` with the same factories, `/restate/scope/{scope}/call|send/…` and the `x-restate-limit-key` header; its scoped `workflowAttach`/`workflowOutput` go to the unscoped workflow route.
- **Java**: scope on the target (`Target.scoped(scope)`, `Target.service(scope, name, handler)`), `Restate.scope(key)` with scoped client factories, `limitKey` in `InvocationOptions`/`Request`; its client puts the scope in the path and the limit key in the `limit-key` query parameter.
- **Python**: `ctx.scope(scope)` returns a `ScopedContext` whose methods take `limit_key`.
- None of them sets a scope on an attach target.
- **`restatedev/e2e` v2.3**: `ServiceToServiceScopeConcurrency` upserts a concurrency rule of 2 on `scope/limitKey` through the admin API, sends four scoped calls through `Proxy.manyCalls` to a JVM-hosted `BlockingProxy.block`, and asserts that exactly 2 run at a time and never more than 2 handlers execute. It fails unless both values reach Restate. The suite sets `RESTATE_EXPERIMENTAL_ENABLE_VQUEUES` and `…_PROTOCOL_V7` for older servers; both are on by default in 1.8.

Restate 1.8.1 (probed): scoped calls, sends (also delayed) and scoped virtual objects work with the default configuration; `sys_invocation` has `scope` and `limit_key` columns. Its ingress has `/restate/scope/{scope}/call|send/{service}[/{key}]/{handler}`, reads the limit key from `x-restate-limit-key` (or `?limit-key=`), and has no scoped attach or output route (`/restate/scope/{scope}/workflow/…` is "bad path"). It does have `POST /restate/lookup`, which computes an invocation id: `{"target": "workflow", "workflowName", "workflowKey", "scope"?}` or `{"target": "idempotentInvocation", "service", "key"?, "handler", "idempotencyKey", "scope"?}` → `{"invocationId"}`. (Restate 1.7.14, probed then, rejected scoped ingress requests with 400 "scoped invocations require vqueues to be enabled".)

## Decision

1. **Scope on the target, limit key on the call** (Java's split, which matches the identity rule): `Target::scoped(string $scope): Target` and `Target::scope(): ?string` (`toArray()` gains `scope`); `limitKey:` (a trailing `?string $limitKey = null`) on `Context::call()`, `callFuture()`, `send()` and `sendAfter()`; `CallOptions::limitKey()`/`withLimitKey()` and `SendOptions::limitKey()`/`withLimitKey()` for `genericCall()`/`genericSend()` and the runtime clients; `ClientRequest::limitKey()` (an option's limit key overrides the request's, like the idempotency key).
2. **`Context::scope(string $scope): Scope`** (the TypeScript/Java/Python entry point): `Restate\Scope` has `name()`, `serviceClient()`, `objectClient()` and `workflowClient()`, whose requests target `Target::…->scoped($scope)`. `ServiceClient`, `ObjectClient` and `WorkflowClient` take an optional scope. No scoped generic call methods: `Target::scoped()` covers them.
3. **Attach targets carry the scope** (shared-core supports it although no official SDK exposes it, and without it a scoped workflow or idempotent request could not be attached to from a handler): `AttachTarget::workflow($name, $key, ?string $scope = null)`, and `AttachTarget::idempotency($target, $key)` takes the target's scope. An invocation id needs none.
4. **The SDK validates the format** (`Restate\Internal\FlowControlKeys`): a scope and each limit key level are 1 to 36 characters from `[a-zA-Z0-9_.-]`, a limit key has at most two levels, and a limit key needs a scoped target. Anything else throws `\InvalidArgumentException` before anything is journaled or sent, naming the rule (Restate rejects such values anyway, and an invalid value in a journaled command would only show up as a failing invocation). The core checks once more what the protocol requires (non-empty values, a limit key only with a scope) with `invalid_argument`.
5. **Removed: Restate 1.8 is required (the SDK advertises v7 as its minimum).** The core used to check the negotiated version before it journaled a scoped call, send, attach or get-output (`Vm::require_v7`) and fail the attempt on v6 with a 573 naming the operation, the target and the Restate version needed, rather than drop the scope (which would change the target's identity silently). No supported server negotiates v6 any more. An empty attach scope is still refused before journaling.
6. **The ingress client gets them too** (TypeScript's shape): `IngressClient::scope($scope)` returns a `Restate\Ingress\Scope` with the three client factories; `ClientRequest::limitKey()`; `limitKey:` on `call()`, `send()`, `sendAfter()`; a scoped `Target` on the generic methods. Scoped requests go to `/restate/scope/{scope}/call|send/…` (delays as `?delay=`), the limit key in `x-restate-limit-key`. **Attaching to a scoped invocation uses `/restate/lookup`**: `WorkflowClient::attach()`/`output()` of a scoped client, `workflowInvocation($workflow, $key, scope: …)` and `idempotentInvocation()` of a scoped target first ask Restate for the invocation id, then use `/restate/invocation/{id}/attach|output` (unscoped targets keep their direct routes, so they cost no extra request). Unlike TypeScript's client, a scoped workflow attach thereby reaches the scoped run. `/restate/lookup` is not used by any official client and not in Restate's documentation; it is in 1.8.1, and the integration test checks that its ids are the scoped invocations' ids. `Restate\Internal\FlowControlKeys` joins the shared types the ingress client may load.
7. **Extension Surface.** The call target has optional `scope` and `limit_key` (only sent when set), the workflow and idempotency attach targets an optional `scope`; the core's `CallTarget` and `AttachTarget` pass them to shared-core.

## Consequences

- The test services' `Proxy` passes `ProxyRequest.scope` (scoped target) and `limitKey` (call or send option) through, and `test-services/exclusions.yaml` is empty: the full conformance suite runs without exclusions.
- Scope and limit key need Restate 1.8, which the SDK requires.
- Implementing `Context` includes `scope()`, and the call and send methods take `limitKey:`.
- The concurrency limiting itself is Restate's; the SDK's part is to deliver the two values. The conformance case `ServiceToServiceScopeConcurrency` checks the limit through the test services; the integration suite checks the values, the per-scope identity of object instances and idempotency keys, and attaching to scoped invocations (`ScopeTest`, `IngressScopeTest`).
