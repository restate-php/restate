# Stray Output

## Status

Accepted. Extends [SDK Logging](0027-sdk-logging.md) with the `restate.output.*` context keys.

## Context

`Endpoint::handle()` sends its status, headers and body with `http_response_code()`, `header()` and `echo`. Without precautions, anything PHP prints earlier in the request goes out first: a handler's `echo`, or a warning, notice or deprecation displayed with `display_errors` on. That is PHP's built-in default without a php.ini, so it includes `php -S` and any container that ships no php.ini. PHP then sends its own headers (`200`, `Content-type: text/html; charset=UTF-8`), the SDK's `header()` calls fail with "headers already sent" (itself another displayed warning), and Restate rejects the response. Against Restate 1.8.1, the ingress reports `500 unexpected content type 'Some("text/html; charset=UTF-8")'; expected content type '"application/vnd.restate.invocation.v7"'` (RT0012) and retries the invocation: for ever without a retry policy on the service, and until the last attempt with `maxAttempts` and `KILL`. Restate's error shows the content type, not the body.

There are two cases:

- **(a) Output printed while the SDK runs the request**, from handler code, a library warning or a deprecation. Nothing has been sent yet, so it can be kept out of the response.
- **(b) Output PHP emitted before the script ran.** The reproduction on record: a request body over `post_max_size` (8M by default) makes PHP print `PHP Request Startup: POST Content-Length of … bytes exceeds the limit of … bytes in Unknown on line 0` during request startup. Restate sends invocation bodies chunked; PHP checks the de-chunked length anyway, and `php://input` still holds the whole body. An `auto_prepend_file` that prints is the same case. Probed with `php -S` (PHP 8.4.20): the startup warning is printed *before* the `output_buffering` buffer is started, so even with `output_buffering=4096` (php.ini-production) the headers are already sent when the script starts, and `headers_sent()` reports file `''`, line `0`. `enable_post_data_reading=0` removes the warning and leaves `php://input` intact (the SDK reads only `php://input`). An `auto_prepend_file` that prints under `output_buffering` does not send headers: its output waits in PHP's buffer.

## Decision

1. **Capture case (a) in `handleHttpRequest()`**, the path shared by `handle()`, `handleRequest()` and the PSR-15 handler. `Internal\OutputCapture` starts an output buffer (`ob_start()` with chunk size 1) before routing and ends it after, in a `finally`. Its callback discards every write and records the byte count, the first 1 KiB, and the `file:line` of the innermost frame that has one at the first write (the callback runs where the output was printed, so for an `echo` that is the `echo`, for `trigger_error()` the line that called it). Buffers request code opened and left open are closed and their contents counted. If request code removed the capture's buffer (an unbalanced `ob_end_*()`), later output was not captured. No output costs one `ob_start()`/`ob_end_clean()` pair per request.
2. **Log it, do not fail the attempt.** The endpoint logs one warning per request, "Discarded output printed while handling the request, which would have corrupted the response; log instead of printing, and set display_errors=Off with log_errors=On", with the request context (`restate.invocation.id` from the header, `restate.request.path`) and `restate.output.bytes`, `restate.output.origin` and `restate.output.excerpt`. The response is the protocol response, unchanged. A removed capture buffer is an error record instead, since the response may be corrupt. Failing the attempt instead would turn a stray `echo` or a deprecation in a dependency into an invocation that never completes, which is what the fix is for.
3. **Detect case (b) in `handle()`, before running the request.** If `headers_sent($file, $line)`, the response cannot be repaired: the status and content type are PHP's, and Restate rejects it whatever the body is. The endpoint then does not run the request at all. A handler run whose output can never reach Restate would execute its `ctx.run` side effects again on every retry without journaling them. It logs an error naming where output started (`file:line`, or "before the script ran: a PHP startup warning, such as a request body over post_max_size, or an auto_prepend_file" when PHP names no file) and the fix: `display_errors=stderr` (or Off) and `enable_post_data_reading=0`. The body is the same diagnostic as plain text instead of protocol frames. Restate's invocation error shows only the content type, so the endpoint's log is where the cause is named. The plain body helps anyone who reads the raw response (curl, a proxy log), and Restate puts a failed discovery response's body into its registration error (as it does for the identity `401`; for this case that is unverified).
4. **Output still in PHP's buffer before `handle()`** (an `auto_prepend_file` under `output_buffering`) is discarded with `ob_clean()` on the innermost buffer and logged as a warning; the response is then correct. Output in an outer buffer, or in one that cannot be cleaned, is logged as an error and stays (removing buffers the runtime set up is not the SDK's call).
5. **The PSR path gets (a) only.** `PsrEndpointHandler` returns a response object; emitting it, and checking what was sent before, is the PSR runtime's job. `headers_sent()` is not a useful signal there: in a long-lived CLI runtime (ReactPHP, RoadRunner, amphp) any startup banner sets it for the life of the process.

## Consequences

- A handler that prints, and any displayed diagnostic during a request, does not break the invocation; the endpoint's log names the source. `display_errors=Off` with `log_errors=On` is still the right setting: it keeps the diagnostics in the server's log and out of the SDK's warning records. (`display_errors=stderr` is not enough under `php -S`: the built-in server prints it into the response.)
- Case (b) still fails every attempt, but visibly: one error record per attempt with the cause and the fix. [SERVING.md](../serving.md#php-settings) documents the settings.
- Output buffers are per process, not per fiber. A runtime that ran two requests' handlers interleaved on fibers in one process would mix their buffers. No supported entrypoint does that: request/response handling is synchronous. A streaming entrypoint would need its own answer ([Bidirectional Streaming](0007-bidirectional-streaming.md)).
- A logger that writes to `php://output` has its records about the request captured and discarded; only the stray-output record itself, logged after the capture ends, reaches the response. Such a logger corrupts the response with or without this change.
- Tests: unit `EndpointStrayOutputTest` (in-process for handler output, the PSR path and buffer handling; child processes for displayed warnings and deprecations, output before the endpoint ran, the `post_max_size` startup warning under `php -S`, `enable_post_data_reading=0`, and `output_buffering`); integration `StrayOutputTest` (a handler that echoes, also inside a run, and one that raises a displayed `E_USER_DEPRECATED` and `E_USER_WARNING`, both complete through Restate). The full matrix (display_errors × enable_post_data_reading × 1, 9 and 31 MiB inputs × a handler that echoes, raises an `E_DEPRECATED` or an `E_WARNING`) is integration `LargeBodyTest`. It confirms case (b) end to end: with display_errors=1 and enable_post_data_reading=1, a 9 or 31 MiB input fails each attempt with `unexpected content type`, the endpoint logs one error per attempt with the origin "before the script ran: a PHP startup warning …", the handler never runs, and the retry policy ends the invocation. Every other cell completes.
