# SDK Logging

## Status

Accepted. Respects the [Public API Boundary](0016-public-api-boundary.md).

## Context

An SDK that logs nothing about its own work leaves the endpoint's side blind: a request that fails with 500, a request rejected with 401 because its identity did not verify, a failed handler attempt (reported to the VM with `notifyError` and retried by Restate), a failed `ctx.run` callback (the attempt ends as a suspension, so the exception goes nowhere), a pause, a suspension and a discovery request with an unsupported version would all pass without a trace. Restate's own log and UI show some of it; an operator looking at the PHP side would see nothing.

What the official SDKs log (TypeScript `492920d`, Java `6b0a96c`, Python `377d634`):

| Event | TypeScript (`endpoint/handlers/generic.ts`, `types/errors.ts`) | Java (`sdk-core`, log4j) | Python |
| --- | --- | --- | --- |
| Attempt starts | info "Starting invocation." / "Replaying invocation." | info "Invocation started" | — |
| Attempt succeeds | info "Invocation completed successfully." | info "Invocation ended successfully" | — |
| Terminal failure | warn "Error when processing a Restate context operation." (every error) | info "Invocation ended with terminal error" | — |
| Retryable failure | warn (same message) | warn "Invocation failed" with the throwable | `logger.exception("Exception in Restate handler")` for unexpected errors |
| Suspension | info "Invocation suspended" | info "Invocation suspended" | — |
| `ctx.run` callback fails (retryable) | warn "Error when processing ctx.run '<name>'." (not for an explicit `RetryableError`) | — | — |
| `PauseError` from a handler | warn (it is ignored there, see [Pause](0021-pause.md)) | — | — |
| 500 from the request handler | error "Error while handling request: <stack>" | warn "Error when handling the request" | — |
| 401, identity not verified | error "Rejecting request as its JWT did not validate: …" | — (thrown as a 401 protocol exception) | — |
| 415, missing content type / unsupported discovery version | warn with the response message | — | — |
| 404, unknown path / service / handler | trace (path), error (service, handler) | warn (path) | — |
| Discovery | — | info "Replying to discovery request with services […]" | — |

Context: TypeScript prefixes every invocation record with `[<target>][<invocation id>]` (`LoggerContext`: `invocationId`, `invocationTarget` = `Service/handler` or `Service/key/handler`); Java puts `restateInvocationId`, `restateInvocationTarget` and `restateInvocationStatus` in the log4j thread context, so user log lines get them too. Neither suppresses the SDK's own records on replay (they are per attempt, not per journal entry); TypeScript's `ctx.console` (the endpoint's logger transport with source `USER`) and Python's `restate.getLogger()` drop user records while replaying. TypeScript's endpoint takes a `LoggerTransport` (`setLogger()`) that receives every record and filters itself; `ctx.console` uses it too.

## Decision

1. **The endpoint takes a PSR-3 logger:** `EndpointBuilder::logger(LoggerInterface $logger)`, and a `$logger` parameter on the shortcuts `Endpoint::fromServices()`, `serve()` and `psr()` (they already take `$identityKeys` the same way). Without one the SDK logs to a `Psr\Log\NullLogger`: nothing. PSR-3 has no way to ask a logger which levels it wants, so the SDK hands every record to the logger and the logger filters, as TypeScript's transport does.
2. **What it logs, and at which level.** Levels follow the official SDKs where they agree, with one deliberate change: the per-attempt lifecycle (start, success, suspension) is `debug`, not `info`. Under request/response serving every suspension is a new HTTP request, so `info` would write two or three lines per request in production for things Restate's UI already shows; a user who wants them enables `debug`.

   | Event | Level | Message | Extra context |
   | --- | --- | --- | --- |
   | Attempt starts | debug | `Starting invocation`, or `Replaying invocation` when the journal holds more than the input | |
   | Attempt succeeds | debug | `Invocation completed` | |
   | Attempt suspends (including a scheduled `ctx.run` retry and a pausing run) | debug | `Invocation suspended` | |
   | Handler throws a `TerminalError` (or the error mapper returns one) | info | `Invocation failed with a terminal error` | `exception` |
   | Handler throws anything else (a `RetryableError`, a VM failure such as a journal mismatch, …) | warning | `Invocation attempt failed; Restate retries it` | `exception` |
   | Handler throws a `PauseError` | warning | `Invocation paused; it waits until it is resumed` | `exception` |
   | A `ctx.run` callback fails and Restate retries it | warning | `Run '<name>' failed; Restate retries it` (under a policy with `OnMaxAttempts::Pause`: `…, or pauses the invocation once the run retry policy is exhausted`) | `restate.run.name`, `exception` |
   | A `ctx.run` callback fails and its retry policy is exhausted (the failure becomes its terminal result) | warning | `Run '<name>' failed and its retry policy is exhausted; the failure is its result` | `restate.run.name`, `exception` |
   | A `ctx.run` callback throws a `PauseError` | warning | `Run '<name>' paused the invocation; it waits until it is resumed` | `restate.run.name`, `exception` |
   | Request identity does not verify (401) | error | `Rejected a request without a valid Restate request identity` | `restate.request.path`, `restate.identity.error` (shared-core's reason; see [Request Identity Through sdk-shared-core](0028-request-identity-shared-core.md)) |
   | Missing content type (415), discovery without a supported manifest version (415) | warning | the response's message | `restate.request.path` |
   | Anything else fails the request (500), including a VM that cannot be created for the negotiated protocol version | error | `Failed to handle the request` | `restate.request.path`, `exception` |
   | Output printed while handling the request, discarded ([Stray Output](0032-stray-output.md)) | warning (error when request code removed the capture buffer) | `Discarded output printed while handling the request, …` | `restate.request.path`, `restate.output.bytes`, `restate.output.origin` (`file:line`), `restate.output.excerpt` (first 1 KiB) |
   | Output PHP sent before `handle()` ran: the request is not run | error | `PHP sent output before the endpoint could respond, …` | `restate.request.path`, `restate.output.origin` |

   Not logged: health checks, discovery that succeeds, unknown paths (404: Restate only calls the paths discovery lists; TypeScript logs them at trace, which PSR-3 lacks; an unknown service or handler under `/invoke/` is a terminal 404 and logged as one), a `TerminalError` from a run callback (the handler decides what it means; if it fails the invocation, that is logged).
3. **Structured context, not formatted prefixes.** Every record about an invocation carries `restate.invocation.id` and `restate.invocation.target` (`Service/handler`, or `Service/key/handler`, the target format of the official SDKs). Before the input is read, the id comes from the `x-restate-invocation-id` header Restate sends and the target has no key; a record about a request carries `restate.request.path` instead of the target. A Throwable is under `exception`, as PSR-3 recommends. Messages are plain text without placeholders; they are not API (like exception messages, see [Public API Boundary](0016-public-api-boundary.md)).
4. **Replay.** The SDK's own records are per attempt and per executed `ctx.run` callback, never per journal entry, so replay does not repeat them: a replayed run returns its journaled result without running the callback, and logs nothing. Like the official SDKs, the SDK does not mute its own records on replay (a retry is worth seeing).
5. **`Context::logger()`** returns the handler's logger: the endpoint's logger in a `ReplayAwareLogger`, as TypeScript's `ctx.console` uses the endpoint's transport. `ReplayAwareLogger` adds `restate.invocation.id` and `restate.invocation.target` to each record (keys the caller passes win), so user records and SDK records about an invocation share their keys; Java gets the same through its thread context. A user who wants another logger still wraps it: `new ReplayAwareLogger($ctx, $logger)`.
6. **Logging cannot break a request.** A logger that throws loses the SDK's record but never fails the request or the attempt (`Endpoint::handleRequest()` promises a response). `Context::logger()` passes the user's own calls through unguarded: those are the user's code.
7. **Without a logger, the SDK does no extra work:** it does not even ask the VM whether the attempt replays to choose the start message.
8. **shared-core's own log events go to the same logger.** shared-core logs through `tracing`; without a subscriber its events are dropped. Its VM logs almost only at `debug` and `trace`: `Start invocation`, `Suspending`, `Executing '…'` for commands (those only while not replaying, `invocation_debug_logs!`), `Failed with error <e>` for every failed transition, a journal mismatch included (the full "Found a mismatch between the code paths …" text, with the command index and both commands), one `warn!` for an unexpected ephemeral notification, and a `trace` span on every VM call.

   What the official SDKs on shared-core do: TypeScript's WASM bindings create one `tracing` dispatcher per VM (`WasmVM::new(…, log_level, logger_id, …)`) with a `fmt` layer filtered at the level of `RESTATE_LOGGING` (default info, also with a custom logger), wrap every VM call in `tracing::dispatcher::with_default`, and hand each formatted line to a JS callback that routes it, by logger id, to the invocation's logger (source `JOURNAL`). Java's FFM core installs one global subscriber at startup whose level comes from the log4j configuration of `dev.restate.sdk.core.StateMachine` and forwards each formatted line through an upcall; the thread's log4j context supplies the invocation keys. Python installs a global `fmt` subscriber that writes to stderr (filter `RESTATE_CORE_LOG`, by default only warnings from its own crate and the tunnel), not to Python logging.

   The PHP extension follows TypeScript, without a callback into PHP:

   - **A capture per VM, one subscriber per process.** `new Vm($headers, $log_level)` gives the VM its own capture: a level and a buffer (`restate_php_core::logs`). The first capture installs one minimal `tracing::Subscriber` (no `tracing-subscriber`) as `tracing`'s global default. While one of the VM's calls runs (`Vm::logged`, around every method body in the extension, and around the VM's creation), its capture is on top of a thread-local stack, and the subscriber hands each event to the capture on top of the calling thread's stack, if that capture's level keeps it. Captures share nothing, and a thread sees only its own stack, so this is safe in a thread-safe (ZTS) build serving concurrent requests; the core tests run captures on several threads, nested captures, and two VMs with different levels on one thread. One subscriber, not a dispatcher per VM as in TypeScript: registering a `tracing` dispatcher takes tracing-core's process-wide dispatcher lock and re-evaluates every callsite against every live dispatcher, so creating a VM would cost time linear in the live capturing VMs, under that lock (measured on a debug build: 4.7 µs per VM with none alive, 449 µs with 5,000). With the one subscriber it is 4.0 µs either way (`restate_php_core/tests/log_capture.rs`, ignored by default).
   - **Buffered, drained after every call.** The subscriber keeps each event at or above the level (never spans: their `trace` instrumentation is not a log line) as level, message, target (the Rust module) and other fields, in a buffer of at most 1000 records (beyond that it counts them and reports one `warn` record "Dropped N shared-core log records …"). `Vm::takeLogs()` drains it. `Extension\Invocation` calls it after every VM call, also when the call throws (a journal mismatch is logged as the call fails), and hands the records to the attempt's `Internal\CoreLogForwarder`, so they reach the logger in order with the SDK's own records: the mismatch comes before `Invocation attempt failed`. No callback from Rust into PHP: re-entering the PHP engine from inside a VM call (where a PHP logger could throw or call the VM again) is what this avoids.
   - **Level.** PSR-3 cannot say which levels a logger wants, so the endpoint picks: `EndpointBuilder::logger($logger, coreLogLevel: LogLevel::INFO)` by default, as TypeScript's default; any PSR-3 level (mapped to `tracing`: emergency to error → `error`, warning → `warn`, notice and info → `info`, debug → `debug`; `tracing`'s `trace` has no PSR-3 level and stays off), or null for none. Records map back: `error` → error, `warn` → warning, `info` → info, `debug` → debug. With shared-core 8.x the default forwards next to nothing (the one `warn!`); `debug` is for investigating, a journal mismatch above all. The shortcuts take the default.
   - **Context.** The attempt's keys (`restate.invocation.id`, `restate.invocation.target`; before the input, what the request said), `restate.core.target` (the Rust module), and each other field as `restate.core.<name>`. Messages as shared-core formats them.
   - **Overhead.** Without a logger (or with `coreLogLevel: null`) the VM is created without a capture: no subscriber, no extra call, and shared-core's events are disabled before they are built (`tracing`'s global level filter stays off in a process that never creates a capture). With one, each attempt allocates a capture. `tracing`'s global lock is taken only when a capture asks for a more verbose level than any before it, at most once per level per process: the subscriber's level hint is the most verbose level asked for so far, and `tracing` then re-evaluates its callsites. Each VM call costs a push and a pop on the thread-local stack, plus one `takeLogs()` call that returns an empty array unless something was logged. Events more verbose than every capture's level are filtered by `tracing`'s level hint before they are built. The rest are checked against the calling thread's capture, which costs a thread-local lookup on threads without one.
   - **Replay.** shared-core suppresses its own `Executing …` lines while replaying; the rest are per attempt.

## Consequences

- New public API: `EndpointBuilder::logger()` (with `$coreLogLevel`), the `$logger` parameter of `Endpoint::fromServices()`, `serve()` and `psr()`, `Context::logger()`. `ReplayAwareLogger` adds the two invocation keys.
- Extension Surface: `Vm::__construct($headers, ?string $log_level = null)` and `Vm::takeLogs()`. Backend Contract: `Backend::newInvocation($headers, ?CoreLogForwarder $coreLogs = null)`. The core crate depends on `tracing` directly (already in the lockfile through shared-core).
- The attempt number is not logged: shared-core keeps the start message's retry count crate-private, and Restate sends no attempt header. The invocation id ties the attempts of one invocation together.
- Evidence: unit `EndpointLoggingTest` (every event above, the context keys, a keyed target, replay, `Context::logger()`, no logger, the core log level and context handed to the backend), `ReplayAwareLoggerTest`, `CoreLogForwarderTest`; core `logs::tests` (levels, fields, no spans, scoping, threads, the buffer limit) and VM tests `tests/vm/logs.rs` (a journal mismatch at debug, start and suspension, nothing above debug, nothing without a level or outside `logged`, two VMs on one thread); extension `SharedCoreLogsTest` (a journal mismatch reaches a PSR-3 logger through `Extension\Invocation` as the call fails; an endpoint on the extension logs it before its own warning) and the `coreLogRecord` shape in `BackendContractTest`; integration `LoggingTest` (Restate 1.8.1, and on FrankenPHP with the ZTS extension, where the whole suite runs with core capture at info: a handler that fails its first attempt logs `Starting invocation`, its own record, `Invocation suspended` at the run, `Replaying invocation` without repeating its own record, the warning with the invocation id and the exception, and `Invocation completed`).
