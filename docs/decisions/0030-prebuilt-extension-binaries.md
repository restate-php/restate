# Prebuilt Extension Binaries

## Status

Accepted. Nothing is published yet: no split repository, Packagist entry, tag or GitHub release exists, and the extension build workflow has not passed on GitHub yet.

## Context

Serving needs the extension (module `restate`, `ext-restate` to Composer, [Extension Versions](../compatibility.md)), and `restate/sdk` requires it, so `composer require restate/sdk` fails until the extension is installed. Building it from source needs a Rust toolchain and libclang, which users of a PHP library should not need. The goal is a prebuilt binary per PHP minor × thread safety × OS × architecture × libc, installed through PIE, the PHP Foundation's extension installer.

PIE builds extensions with `phpize`, `./configure` and `make`; it cannot build a Cargo crate. Its one other Unix route is the `pre-packaged-binary` download method: the package's `composer.json` says so, and PIE downloads a prebuilt archive from the GitHub release of the package's version instead of building ([PIE's maintainer docs](https://github.com/php/pie/blob/1.5.5/docs/extension-maintainers.md#pre-packaged-binary)).

### What PIE does (read in PIE 1.5.5, tag commit `a641e66`; 1.6.0-rc.4 is unchanged here unless noted)

- **Asset name** (`src/Platform/PrePackagedBinaryAssetName.php:22-51`). PIE builds a list of candidate names from the PHP it installs into and takes the first release asset whose name, lowercased, is in the list (`src/Downloading/GithubPackageReleaseAssets.php:53-67`): `php_{extension}-{version}_php{major.minor}-{arch}-{os}-{libc}{debug}{ts}.{zip|tgz}`, where
  - `{version}` is the package's Composer *pretty* version (`src/DependencyResolver/Package.php:79`), i.e. the tag as Packagist lists it: tag `0.1.0` gives `0.1.0`, tag `v0.1.0` gives `v0.1.0`;
  - `{arch}` comes from `php_uname('m')`: `x86_64`/`amd64`/`x64` → `x86_64`, `aarch64`/`arm64` → `arm64`, anything else `x86` (`src/Platform/Architecture.php:19-26`, `src/Platform/TargetPhp/PhpBinaryPath.php:410-441`);
  - `{os}` is `PHP_OS_FAMILY` lowercased (`linux`, `darwin`, …);
  - `{libc}` is `bsdlibc` when `otool` exists, `musl` when the output of `ldd ls` contains "musl", otherwise (and on any error) `glibc` (`src/Platform/LibcFlavour.php:47-70`);
  - `{debug}` is `-debug` for a debug build of PHP and empty otherwise: PIE never asks for `nodebug`, although the docs list it;
  - `{ts}` is `-zts` for a thread-safe PHP; for NTS both an empty suffix and `-nts` are candidates. Thread safety is read from `php -i` ("PHP Extension Build => API…,NTS", `src/Platform/TargetPlatform.php:52-110`).

  After those four (zip and tgz, with and without the NTS suffix) come `anylibc` fallbacks for Linux. A release that has both a zip and a tgz for the same target serves whichever comes first in the release's asset list.
- **Where it looks.** `GET https://api.github.com/repos/{owner}/{repo}/releases/tags/{version}` (`src/Downloading/GithubPackageReleaseAssets.php:69-112`; the API base is fixed in `src/Container.php:158-169`). `{owner}/{repo}` is parsed from the package's dist URL as Packagist publishes it (`https://api.github.com/repos/<owner>/<repo>/zipball/<sha>`), or is the package name when the dist URL contains it (`src/DependencyResolver/Package.php:144-165`). GitHub's "get a release by tag name" returns published releases only, so a draft release is invisible to PIE. Only GitHub is supported (the code carries a todo for other hosts).
- **Download.** The asset's API URL with `Accept: application/octet-stream`; a `.tgz` switches Composer's dist type to `tar` (`src/ComposerIntegration/Listeners/OverrideDownloadUrlInstallListener.php:150-170`). Composer then extracts it like any dist archive.
- **Archive layout.** After extraction PIE expects `<extension>.so` at the top: `restate.so` (`src/Building/UnixBuild.php:55-71`). Nothing else in the archive is used. (Composer moves the contents of a single top-level directory up, but `restate.so` at the root is what was tested.)
- **Install** (`src/Installing/UnixInstall.php:58-127`): removes an existing `restate.so` from `extension_dir`, copies the new one there (with `sudo` when the directory is not writable), then enables it with the first approach that works, each one checked by loading the extension into the target PHP (`src/Container.php:187-195`, `src/Installing/Ini/`): already loaded; `phpenmod` (ondrej packages); `docker-php-ext-enable` (official images, writes `docker-php-ext-restate.ini`); a new `80-restate.ini` in the additional ini directory; the single `php.ini`. If none loads the extension, the `.so` stays installed and PIE prints "You must now add extension=restate to your php.ini", without the loader's reason.
- **Integrity.** None beyond HTTPS: PIE prints "dist-sha integrity check is not available for prebuilt-binary URLs; HTTPS to the release-asset origin is the only integrity guarantee" (`OverrideDownloadUrlInstallListener.php:159-166`; 1.6.0-rc also clears the dist mirrors and SHA-1, which would otherwise apply to the source zipball). It records the installed file's SHA-256 only to notice later changes (`src/File/BinaryFile.php`, `pie show`). It verifies GitHub artifact attestations for its own PHAR (`src/SelfManage/Verify/`), never for extensions.
- **Package metadata.** `php-ext.support-zts`/`support-nts` default to true; `os-families` refuses other operating systems before downloading anything (`src/DependencyResolver/ResolveDependencyWithComposer.php:81-101`); the package's `require.php` is resolved against the target PHP like any Composer constraint. On Windows PIE ignores `download-url-method` and always looks for a Windows DLL archive (`src/Downloading/DownloadUrlMethod.php:114-130`). With `pre-packaged-binary` as the only method, configure options make the install fail (`OverrideDownloadUrlInstallListener.php:105-112`) and `pie build` fails (1.6.0-rc docs); neither applies to an extension without configure options that is only installed.
- **Repository content.** PIE replaces the source zipball with the release asset before downloading, so a `pre-packaged-binary`-only package needs nothing in its repository but `composer.json` (Packagist needs that).

### What was built and tried

Release builds (`bin/build-extension.sh --release --php-config …`) inside the official images on Linux x86_64, then loaded with `php -n -d extension=…` and smoke-tested (handshake functions, a `Vm` constructed with an invocation content type answers status 200):

| cargo-zigbuild, glibc 2.28 target, Debian trixie | `php:8.4-cli-trixie`, `php:8.5-zts-trixie` | 2.53 MB | 1.09 MB | `libc.so.6`, `libpthread.so.0`, `libdl.so.2`, `ld-linux-x86-64.so.2` | `GLIBC_2.28` | bullseye (PHP 8.4.11, glibc 2.31), bookworm, trixie, the dev shell's PHP 8.4.20 |
| gcc, Alpine (musl) | `php:8.4-cli-alpine`, `php:8.4-zts-alpine`, `php:8.5-zts-alpine` | 2.97 MB | 1.20 MB | `libc.musl-x86_64.so.1`, `libgcc_s.so.1` | — | a clean `php:8.4-cli-alpine` (Alpine 3.24, which has `libgcc`) |

Each release build took 50–130 s on a loaded 12-core machine. The zig-linked module, built in `php:8.4-cli-trixie` (PHP 8.4.27) and loaded into the dev shell's PHP 8.4.20, passed the extension suite (`--testsuite extension`, 192 tests) and the integration suite against Restate 1.8.1 (`RESTATE_PHP_EXTENSION_PATH`, 106 tests); the panic guard (`catch_unwind` with `panic = "unwind"`) works in a zig-linked debug build (`Vm::sysRun('__restate_php_panic_probe__')` throws `ExtensionException: Rust panic: restate panic probe` and a fresh VM still works), so zig's own unwinder replaces `libgcc_s`.

- **cargo-zigbuild needs libclang 18 or newer.** In `php:8.4-cli-bookworm` (clang 14) bindgen crashed parsing `wrapper.h` with zig 0.15's header flags, which cargo-zigbuild appends to `BINDGEN_EXTRA_CLANG_ARGS` (overriding the variable does not remove them; its README says zig 0.15 needs clang 18+ for bindgen). The trixie images (clang 19) work. ext-php-rs's C wrapper is compiled by `zig cc` without changes.
- **Patch releases.** A module built against 8.4.27's headers loads into 8.4.11 and 8.4.20. A zig *debug* build did not load into 8.4.11 (`undefined symbol: _femalloc`, a Zend allocator function that 8.4.27's `zend_alloc.h` declares and 8.4.11 lacks): the debug build keeps references to every bound function, the release builds reference none of the newer ones (`nm -D --undefined-only`).
- **zip needs unzip.** With a `.zip` asset, `pie install` failed in `php:8.4-cli-bookworm` with both the PHAR and PIE's static binary (`pie-Linux-X64`): "The zip extension and unzip/7z commands are both missing". Composer extracts a zip only with `ext-zip` or `unzip`, which the official PHP images and PIE 1.5.5's static binary lack; it extracts a tgz with `PharData`, which PIE itself runs on. With `unzip` installed the zip worked; the tgz worked everywhere without it.
- **PIE, end to end, without GitHub.** PIE has no way to install a prebuilt binary from a local file or repository: the release lookup is hard-wired to `api.github.com`. The test served a fake `api.github.com` and a Composer repository over HTTPS from Caddy inside the target container (the container's `/etc/hosts` and CA store pointed at it), with Packagist removed (`pie repository:remove packagist.org`, `pie repository:add composer https://repo.test`). The repository listed `restate/ext-restate` 0.1.0 from `extension/composer.json` with a Packagist-style dist URL (`https://api.github.com/repos/restate-php/ext-restate/zipball/<sha>`, so PIE derived the release repository from it), and the fake release `0.1.0` carried six archives (8.4 and 8.5 × NTS and ZTS glibc, 8.4 NTS and ZTS musl). `pie install restate/ext-restate:0.1.0` (1.5.5, PHAR and static binary) picked the matching archive, installed `restate.so` into `extension_dir`, enabled it through `docker-php-ext-enable` and checked it loads, in `php:8.4-cli-bookworm`, `php:8.4-zts-bookworm`, `php:8.5-cli-bookworm`, `php:8.4-cli-alpine` and `php:8.4-cli-bullseye` (the glibc-2.28 archive); `php -m` listed `restate` and `pie show` the package. With the bookworm-built (glibc 2.34) archive, PIE on bullseye installed the file, failed to enable it ("Expected extension restate to be loaded … but it was not detected") and told the user to edit php.ini.

### Cross-compiling with Nix

The builds above run in one image per target, on a runner of the target's CPU. ext-php-rs's build script never runs the target's PHP, though. It reads four entries of `php -i` (version, PHP API, thread safety, debug build) and `php-config --includes`, then runs bindgen over the headers. So every target can be cross-compiled from one machine with zig, given headers for that target. [ext-php-rs.nix](https://github.com/sagikazarmark/ext-php-rs.nix) does that (its README has the details; it was developed in this repository as `nix/ext-php-rs/` before moving there), and from macOS (arm64) and Linux (x86_64) it built all 16 archives:

- **The headers must be configured for the target.** Feeding bindgen headers from another platform or flavor changes the layout of structs ext-php-rs binds, without any error:
  - NTS headers with `ZTS` defined miss the executor globals' timer fields (`ZEND_MAX_EXECUTION_TIMERS`, set by a ZTS configure on Linux).
  - macOS headers give Linux targets wrong core globals (`tmp_host_*` fields).
- **What is used instead:** nixpkgs' PHP source, run through `./configure` for the target with `zig cc` and no extensions (`--disable-all`). Nothing is compiled, and it takes about a minute per target. Two checks that run a program get the answers a gcc-built PHP on Linux gets:
  - `php_cv_have_stack_limit=yes`: a cross configure answers no and drops `ZEND_CHECK_STACK_LIMIT` (the executor globals' call stack fields).
  - `php_cv_have_global_register_vars=yes`: clang has no global register variables. The answer selects the Zend VM kind, and with it PHP 8.5's `zend_vm_opcode_handler_t`.

  With both, the bindings bindgen generates (the Zend API as ext-php-rs sees it) are identical to those generated from the official images' own headers for all 16 targets. Without the second, PHP 8.5's differ in that one type.
- **libclang must match zig's LLVM.** cargo-zigbuild gives bindgen zig's builtin headers. On aarch64, PHP's headers include `arm_neon.h`, which only libclang of zig's own LLVM version parses ("Unable to generate bindings for PHP"). This includes zig 0.15.2 with Debian trixie's libclang 19, the combination the per-image arm64 glibc builds would have used. Nix takes libclang from zig's build inputs.
- **ext-php-rs passes the macOS SDK to bindgen** whenever its build script runs on macOS, even for a Linux target. The cross builds hide `xcrun` from it.
- **Results:**
  - Release modules are 2.1–2.5 MB, and archives 1.0–1.1 MB.
  - glibc modules need `libc.so.6`, `libpthread.so.0`, `libdl.so.2` and the loader, with `GLIBC_2.28` as the newest symbol.
  - musl modules need only `libc.so` (zig's name for musl's C library, which musl's loader resolves to itself). They need no `libgcc_s`: zig links its own unwinder in.
  - Built on Linux x86_64, every module loads and constructs a `Vm` in a clean official image of its target (Docker emulating x86_64 and arm64 on macOS). The glibc ones for PHP 8.4 also load into `php:8.4-cli-bullseye` (glibc 2.31, PHP 8.4.11, older than the 8.4.27 headers), on both CPUs.
  - Cross-compiled debug modules pass the extension suite (200 tests) and `ExtensionPanicTest` (the panic guard) in `php:8.5-zts-alpine` arm64 and `php:8.4-cli-trixie` x86_64.
  - A build reproduces itself on the same build platform: the build directory, random on macOS, is remapped in panic locations. Builds on macOS and Linux differ byte for byte.

## Decision

1. **Distribution: PIE with prebuilt binaries only.** Users run `pie install restate/ext-restate`; Packagist lists `restate/ext-restate` from a read-only extension repository split from this one; each extension version is a GitHub release of that repository whose assets are the prebuilt archives. `composer.json` sets `"download-url-method": ["pre-packaged-binary"]` and no fallback: `composer-default` would make PIE run `phpize` on the repository, which has nothing for it to build. Building from source stays `bin/build-extension.sh` in this repository (or `cargo build --release -p restate` in the extension repository, then copy `librestate.so` to `restate.so`).
2. **`extension/composer.json` is the package**, and `extension/` is what splits into the extension repository, so that repository's root has `composer.json` next to the Cargo workspace (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/config.toml` and both crates): the source of the binaries, at the tag they were built from. Nothing moves, so Cargo paths, `docker/Dockerfile`, the scripts and the CI cache keys stay as they are. Rejected: `packages/ext-restate/composer.json` alone (fits the `packages/` layout, but the extension repository would carry no source) and moving the crates under `packages/ext-restate/` (churn everywhere for the same split). The package:

   ```json
   {
     "name": "restate/ext-restate",
     "type": "php-ext",
     "license": "MIT",
     "require": { "php": "~8.4.0 || ~8.5.0 || ~8.6.0" },
     "php-ext": {
       "extension-name": "restate",
       "download-url-method": ["pre-packaged-binary"],
       "os-families": ["linux"]
     }
   }
   ```

   plus a description. `support-zts` and `support-nts` keep their default (both). `os-families: ["linux"]` makes PIE on macOS, Windows and the BSDs refuse the package up front instead of failing to find an archive. The `php` constraint is the packages' (decision 2 of [Composer Metadata](0026-composer-metadata.md)): a new PHP minor is added to both, and to the release matrix, in one change. `composer check:packages` validates the file (`composer validate --strict`) and checks its name, type, `extension-name` against the loaded module and its `php` constraint against the root's. The root `composer.json` does not replace it (the root never requires the extension).
3. **Archives: `.tgz` with `restate.so` at the root**, named `php_restate-<version>_php<minor>-<arch>-linux-<libc>-<nts|zts>.tgz`, for example `php_restate-0.1.0_php8.4-x86_64-linux-glibc-nts.tgz`. A tgz works with PIE in the official images out of the box, a zip does not; only one format, so the asset order never decides. The NTS archives carry `-nts` (both forms match; the explicit one is unambiguous to people). No debug builds: PIE on a debug PHP finds no archive. Every archive has a `.sha256` file in the workflow, and the release a `SHA256SUMS`. ext-php-rs.nix's `mkPieArchive` writes the archive and its checksum, naming it the way PIE does (PHP minor, CPU, C library, thread safety) from what the module was built for.
4. **The matrix: PHP 8.4, 8.5 and 8.6 × NTS and ZTS × x86_64 and arm64 × glibc and musl, Linux only: 24 archives per release.** Cross-compiled with Nix ([Cross-compiling with Nix](#cross-compiling-with-nix)): the extension flake's `packages.pie` (`extension/flake.nix`, `devenv build outputs.pie`, `composer build:pie`), built with [ext-php-rs.nix](https://github.com/sagikazarmark/ext-php-rs.nix), a flake that knows nothing of this project ([Extension Flake](0037-extension-flake.md)). The build runs the same on any platform, so one CI job builds all of them, and a release can be rebuilt on a laptop. Each target's headers are nixpkgs' PHP source, configured for that target; the PHP patch releases are nixpkgs' (`extension/flake.lock`). Rejected: building in the official images on runners of each CPU, the previous approach. It needs 16 jobs, arm64 runners and tools downloaded per image, and it ran into the libclang/zig mismatch on arm64. Also rejected: headers copied from the official images. They match, but they tie the build to a container registry and image tags, and nixpkgs has the source.
5. **glibc floor 2.28**, by linking with cargo-zigbuild against glibc 2.28 (ext-php-rs.nix's glibc targets; zig and cargo-zigbuild from nixpkgs, with the libclang of zig's own LLVM). A plain build links against the build image's glibc and needs 2.34 when built on bookworm (2.41 symbols are possible on trixie), which leaves out RHEL/Rocky/Alma 8 (2.28, supported until 2029, with PHP 8.4 and 8.5 from Remi), Debian 11 and Ubuntu 20.04 (2.31), where PIE would install a module that does not load. 2.28 is the glibc of the oldest distribution still in standard support that can install PHP 8.4 (RHEL 8 and its rebuilds); older ones (Amazon Linux 2, Ubuntu 18.04) are past standard support. The cost is a second linker (zig) for the prebuilt binaries next to the dev shell's. The extension suite and the panic guard were run against zig-linked modules (glibc and musl). Each build checks its module's newest glibc symbol version against the floor, and so does the workflow. Building on an old distribution instead is not possible: the official PHP 8.5 images have no bullseye variant, and 8.4's bullseye image stopped being updated in August 2025.
6. **musl: supported**, linked with zig against musl (`.cargo/config.toml` already turns off `crt-static` for musl, which a `cdylib` needs). The module needs only `libc.so`, which musl's loader resolves to itself. zig links its own unwinder in for `panic = "unwind"`, so unlike a module built with Alpine's gcc it does not need `libgcc_s.so.1`, and works on a minimal Alpine too.
7. **macOS: not yet.** ext-php-rs supports macOS, `.cargo/config.toml` already links with `-undefined dynamic_lookup`, and `devenv build outputs.extension` builds and loads the module on macOS against Nix's PHP. ext-php-rs.nix (v0.1.0) now cross-compiles macOS modules (`x86_64-darwin`, `aarch64-darwin`, minimum macOS 11.0) and names their archives for PIE, and its CI loads them into setup-php's PHP. Adding them means adding those targets to `packages.pie` in `extension/flake.nix`, `darwin` to `os-families`, and macOS runners to the workflow's verify matrix. None of that has been tried with this extension, or against Homebrew's PHP.
8. **Windows: out of scope.** PIE on Windows ignores `download-url-method` and installs only DLL archives named after the Visual Studio version (`php_restate-<version>-<php>-<ts>-<vs>-<arch>.zip`), built against the PHP SDK of `php/php-windows-builder`; the extension has never been built or tested on Windows, and its serving model (php-fpm, FrankenPHP) is Linux-first. `os-families: ["linux"]` keeps PIE on Windows from trying.
9. **Integrity: checksums and provenance on the release, HTTPS for PIE.** PIE checks nothing but HTTPS, so the release workflow publishes `SHA256SUMS` and creates [artifact attestations](https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations) for every archive (`actions/attest-build-provenance`), which a user can check with `gh attestation verify <archive> --repo <this repository>` before or after installing. If PIE learns to verify attestations, they are in place.
10. **Build and release workflows.** `.github/workflows/extension.yaml` builds the 24 archives in one job in the dev shell (`composer build:pie`), where each Nix build checks its module's shared libraries (only the C library, which is all PIE can install) and glibc floor. Then one job per CPU, on a runner of that CPU (`ubuntu-24.04-arm` for arm64):
    - checks every archive's checksum
    - loads each archive of that CPU into a clean official image of its PHP minor, thread safety and C library, with the module alone (`php -n`), and runs `extension/tests/*.phpt` there: the flake's `load-test`, ext-php-rs.nix's `loadPieArchives`, which also fails on a name it cannot parse, the names PIE matches exactly
    - PHP 8.6's official images are ZTS only (`8.6-cli-*` is ZTS; there is no `8.6-zts-*`), so the 8.6 NTS glibc archive runs the same tests with nixpkgs' PHP 8.6 (at `extension/flake.lock`'s nixpkgs), and the 8.6 NTS musl archives are not loaded: nothing packages an NTS PHP 8.6 for musl yet.

    A job on macOS runs the flake's checks there ([Extension Flake](0037-extension-flake.md)).

    It runs on changes to `extension/` (which holds the flake) or the devenv files, by hand, and from the release workflow, and uploads nothing. `.github/workflows/release.yaml` attests the archives, writes `SHA256SUMS` and publishes them on the extension repository's GitHub release, together with the packages ([Release](0031-release.md)). The release is created as a draft, which can take assets even when the repository has immutable releases, and published once complete, since PIE sees published releases only.
11. **Versions and tags.** The extension is released with the packages at one version ([Release](0031-release.md)), and the extension repository's tag is the bare version, `0.1.0`: PIE puts the tag, as Packagist reports it, into the asset name, and the archives are named after `phpversion('restate')`. A tag `v0.1.0` in the extension repository would make PIE look for `php_restate-v0.1.0_…`.

## Consequences

- Installing the extension needs PIE and nothing else: no Rust, no libclang, no build tools. `pie install restate/ext-restate` picks the archive for the user's PHP minor, thread safety, CPU and libc, installs it and enables it.
- Users outside the matrix (macOS, Windows, BSD, debug PHP, glibc older than 2.28, PHP minors the constraint does not list) get a refusal or "no archive found" from PIE and build from source.
- Each release produces 24 archives of about 1.0–1.1 MB.
- Adding a PHP minor touches `extension/composer.json`, every `packages/*/composer.json`, the root `composer.json`, `phps` in `extension/flake.nix` and the workflow's verify matrix in one change. nixpkgs must have that PHP (`php86`, …).
- The release depends on nixpkgs (zig, cargo-zigbuild, PHP's source, pinned by `extension/flake.lock` through ext-php-rs.nix). It uses the official PHP images (tags, not digests) only to check the archives: a module built against one patch release loads into the others, as long as the extension uses no function added in a later patch release.
- Building the prebuilt binaries needs Nix and devenv, not Docker. Loading them needs a Linux machine of each CPU, or emulation.

### Risks

- **Packagist metadata and the asset names must agree.** A `v` prefix on the extension repository's tag, or a Packagist dist URL that does not name the extension repository, breaks every install ("could not find release asset"). Only a real release shows this.
- **A newer-patch symbol.** If the extension, or a newer ext-php-rs, starts calling a Zend function added in a later patch release, the archive requires that patch release, and PIE installs a module that fails to load on older ones, with the unhelpful message seen above. The archives are built against nixpkgs' patch release (8.4.27 and 8.5.12 at the time of writing), which trails the newest. The release modules for PHP 8.4 load into 8.4.11, and the workflow loads each module into the newest image only.
- **Configure drift.** The headers come from a cross configure with two answers preset. A new PHP release could add a configure check that changes a struct ext-php-rs binds and that a cross configure answers differently, without any error. Comparing the bindings (each build's `share/ext-php-rs/bindings.rs`) with those generated from the official images' headers catches it. That was done once for all 16 targets, by hand, and no workflow does it.
- **PIE versions.** Asset matching, the extraction formats and the GitHub-only lookup are PIE internals (`@internal` in its code); PIE 1.6 is in release candidates. The decision relies on the documented naming convention and on the behaviour above.
- **Not verified:** the workflows on GitHub, including the Nix build on the runner, the arm64 verify jobs (the arm64 modules were loaded under emulation only), artifact names, the attestation step, the token's permissions and the release creation. Also: the real GitHub API and asset download (redirect to the asset host, anonymous rate limits; PIE uses Composer's GitHub token when one is configured), Packagist's metadata, PIE outside Docker images (the `phpenmod` and plain ini paths, `sudo`), and `pie install` in a project that requires `restate/sdk` (PIE then searches Packagist for a package providing `ext-restate`).
